# Prompt de démarrage — BamanaShop

Lis d'abord AGENTS.md, ROADMAP.md, STATUS.md et tous les documents de docs/. Inspecte le dépôt et les outils installés avant de modifier quoi que ce soit. Le produit est une marketplace généraliste à Conakry, en GNF, avec exactement deux apps mobiles : BamanaShop Customer et BamanaShop Pro (vendeurs + livreurs). BamanaShop Admin est un dashboard web interne. Backend partagé Supabase/PostgreSQL. MVP : panier mono-vendeur, livraison par partenaires avec dispatch manuel, COD et Orange Money uniquement après validation des accès. Aucun wallet, aucun split-payment présumé, aucune transaction réelle pendant le bootstrap.

Travaille sur la branche de préparation actuelle ou crée une branche dédiée depuis elle ; jamais directement sur main. Lance exactement quatre sous-agents avec ownership strict selon docs/WORKSTREAMS.md : (1) Platform : supabase/**, packages/contracts/**, packages/domain/**, supabase/tests/** ; (2) Customer : apps/customer/** ; (3) Pro : apps/pro/** ; (4) Admin + QA : apps/admin/**, tests/**, docs/qa/**. L'orchestrateur seul gère les fichiers racine, pnpm workspace, configs partagées, CI, intégration et revue. Aucun agent ne modifie les fichiers d'un autre.

Commence par établir les contrats communs et un plan d'intégration. Construis le socle exécutable du monorepo TypeScript avec pnpm, les trois applications, les packages partagés et Supabase local/dev. Les trois apps doivent démarrer avec des données fictives typées et des états loading/empty/error. Implémente en parallèle le modèle initial, les rôles, memberships, RLS et tests d'isolation. Customer couvre découverte, catalogue, boutique, panier mono-vendeur et checkout mocké. Pro couvre deux espaces séparés par rôle : gestion boutique/produits/commandes pour vendeur ; missions assignées, collecte, preuve et incident pour livreur. Admin couvre modération, commandes, dispatch, rapprochement et payables, sans exposer de données inutiles. N'implémente aucun faux succès de paiement ou de reversement.

Avant de coder, confirme les versions/outils par leurs documentations actuelles, vérifie Node/pnpm/React Native Community CLI/Android SDK/Supabase disponibles et respecte les contraintes de la machine. Ne suppose aucun endpoint de paiement ou de livraison ; crée des interfaces/adaptateurs mockés. Les montants sont des entiers GNF, les règles financières sont côté serveur, snapshots immuables et journal financier auditable. RLS doit protéger chaque table exposée ; aucun secret privilégié dans les clients.

Travaille en petites étapes. Ajoute tests unitaires, intégration DB/RLS et tests de parcours utiles. Exécute lint, format check, typecheck, tests et builds disponibles ; ne prétends pas avoir passé un check non exécuté. Vérifie git diff et git status. Mets ROADMAP.md et STATUS.md à jour avec les livrables réels, les commandes exécutées, les résultats, les blocages et la prochaine tâche. Termine par un rapport précis : architecture créée, fichiers modifiés, commandes et résultats, points non vérifiés, risques et PR/branche. Si une dépendance manque ou un accès externe est absent, livre les parties indépendantes et documente le blocage au lieu d'inventer une intégration.
